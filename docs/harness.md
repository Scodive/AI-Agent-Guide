# Agent Harness：Coding Agent 如何工作

*本期新增论文资料核对：2026-11-23；其他论文沿用各条记录日期；两项 Codex 架构资料核对：2026-11-02。仅刷新下文 Agents API 架构页与 Codex as a platform；长任务案例、overview 等其他产品资料沿用 2026-09-27。旧论文日期见论文库。*

**Harness（运行框架）**是围绕模型组织任务、工具、执行环境和反馈的程序。模型决定下一步要做什么；harness 决定它能看到哪些信息、怎样调用工具、命令在哪里执行、结果如何回到上下文，以及何时验证、停止或请人介入。不要把模型、harness、执行环境和评测任务混成一个“Agent 能力”数字。[OpenAI 官方 Agents API 架构说明](https://developers.openai.com/api/docs/guides/agents-api/architecture)在该托管 API 的范围内明确区分 harness、environment 和 application server；[Code as Agent Harness](https://arxiv.org/abs/2605.18747)从研究角度梳理这些层次。

## 一个 Coding Agent 的工作循环

1. **接收任务和仓库上下文**：目标、约束、文件、已有差异、项目说明和可用工具进入会话。
2. **选择动作**：模型根据当前上下文提出检索、读取文件、编辑代码或运行命令等动作。
3. **执行并观察**：harness 把动作交给有权限的工具或沙箱；输出、错误和文件变化返回会话。
4. **验证与修复**：运行相关测试、构建或人工可检查的演示；失败时根据反馈修改，而非只凭“代码已写”结束。
5. **交付与监督**：展示差异、验证结果及剩余风险；需要权限或方向判断时交由人决定。

**先看固定流程基线。**[Agentless](https://arxiv.org/abs/2407.01489)把仓库修复组织为定位、补丁生成、验证三个预定阶段，模型不自主决定下一种工具动作；程序仍执行检索、测试和候选筛选。对照 SWE-agent 的动态动作循环与 SWE-Search 的分支搜索，问新增自由度解决了什么失败、花了多少预算。Agentless v2 的 SWE-bench Lite 结果是历史快照，且每题最多生成 40 个补丁和 40 个复现测试；固定流程也有采样成本，不能直接用异模型榜单证明其总是更优。[完整记录](papers.md#paper-2407.01489)。

这是一种**概念性拆解**，不是某个产品内部代码的逐行复刻。[OpenAI 对 Codex 长任务的说明](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)将其概括为计划、编辑、运行工具、观察、修复和重复；[官方 Agents API 文档](https://developers.openai.com/api/docs/guides/agents-api/overview)说明 Codex harness 管理会话、编排、上下文压缩与恢复，执行环境负责命令和文件。Codex 是帮助理解这一结构的实例，不等于所有 Coding Agent 共用同一实现。

## 运行中修改的生命周期

[Meta²](https://arxiv.org/abs/2611.05139)把可复用指导与本次运行状态分开。训练时对比无演化、当前指导的演化、可见特权训练反馈的演化，提炼act/hold/avoid条目。部署时指导冻结；检查点可KEEP，也可通过提示、钩子或工具通道作有范围的修改，保留当前沙箱与任务进度。任务结束丢弃这些编辑，下一次运行重新加载种子Harness。

这让“什么需要持久化”成为明确设计问题。论文中持续携带所有局部编辑的消融反而降分；但这是所测工作负载的结果，不是应当丢弃全部经验的通则。Terminal测试60题各5次、DeepSWE测试75题各3次是推理重复；每个骨干分别学指导，不是同一指导零样本跨模型迁移。A/B/C对比来自不同整条轨迹，不能把终局差异归因给某一次编辑；检查点与返工的调用费用仍计入。见[记录](papers.md#paper-2611.05139)和[RSI的继承面](rsi.md#可复用指导与任务内编辑)。

## 记忆与仓库状态分别传给下一任务

[CoReMem](papers.md#paper-2611.17316)把当前任务留下的仓库树与记忆文本分开：比较有无记忆时，下一任务从同一个继承状态开始。先用轨迹分段移除找出值得保留的定位与检查锚点，再区分固定actor使用紧凑记忆和另做参数后训练。总token包含记忆模块的写读调用；缓存计价token与原始token也分别报告。

这补上“保存经验→减少后续重找”的检验。复制文件路径不证明单步因果贡献，锚点门控只是来源使用的代理。其主要证据是Python仓库/mini-swe-agent，测试48链/96边界，各模型重复次数不同；OpenHands扩展仅94/96边界且用原始token，不能与主表直接拼接。延迟、能耗及更长历史的刷新策略仍待验证。

## 近期延伸阅读（2026-10-03）

- [Beyond the Model](https://arxiv.org/abs/2609.32459)：先看固定模型的框架比较，再看组件消融。读图时分清基准总规模与实际抽样数；压缩和通用子 Agent 在所测仓库生成任务中可能降分。
- [Mingbird](https://arxiv.org/abs/2610.02001)：看工具预填充、循环检测与完成检查如何适配小模型。主实验只在一台 Windows 机器上进行；单组件结果的波动限制了归因。
- [VISTA](https://arxiv.org/abs/2610.02200)：将 Harness 视角延伸到视觉交互。核心是保留原始帧并主动回看、放大和读取像素；公开游戏成绩仍需留出环境检验。

这些是拓展阅读，均按预印本记录；完整实验范围见[论文库](papers.md)。

## Codex 的托管 API 与本地集成

官方 [Agents API 架构页](https://developers.openai.com/api/docs/guides/agents-api/architecture)中，OpenAI 托管 Codex harness 的循环和会话；environment 提供命令和文件计算；application server 组织产品任务、事件和应用工具。自有环境还需要应用方管理创建、重连、关闭与文件保存。没有执行环境时，仍可使用远端 MCP/函数工具，但不能据此假设有 Bash、apply_patch 或工作区文件能力。

官方 [Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform)另介绍 `codex exec` 的非交互任务、SDK 的程序集成和 app-server 的持久会话/事件/中断与审批。本地进程集成与上面的托管 API 要分别说明；业务规则、数据访问和授权仍由具体应用及运行设置落实。两页于 2026-11-02 核对，是接口与职责说明，不是性能实验或对所有 Codex 运行方式的统一承诺。

## 阅读 Codex 时应分清的边界

- **Codex 模型与 Codex harness**：模型产生判断与工具请求；harness 维护循环和会话，连接工具与执行环境。不同运行方式提供的工具、权限和环境可能不同。以上以[OpenAI 官方架构文档](https://developers.openai.com/api/docs/guides/agents-api/architecture)为准。
- **仓库指令与验证**：`AGENTS.md`、技能或任务说明可以给出项目约束；它们不能代替运行测试、检查差异和确认交付条件。[OpenAI 的长任务案例](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)是一个有说明文件和阶段验证的实例，不是所有任务的效果保证。
- **安全边界**：工具可访问的文件、网络与凭据取决于执行环境；评估 Coding Agent 时应记录权限、沙箱和人工审批设置。[官方环境文档](https://developers.openai.com/api/docs/guides/agents-api/architecture)区分托管与自有执行环境。

**推荐顺序：**先用 Agentless 理解固定流程，再用 SWE-agent 理解动态动作与接口，读 Codex 官方架构理解产品中的循环，之后用 The Scaffold Effect 和 DAREBench 检查模型、框架和工作负载的比较边界。相关论文的研究问题、指标、局限与核验日期见[论文库](papers.md)。

## 筛选领先与确认改进

[Contain, Conform, Compare 扩展论文](papers.md#paper-2611.16485)区分三项检查：隔离执行Agent生成的代码；核对工具结果角色、历史字段、采样、模板与实际token；在相同任务和重复次数上配对比较候选与基线。只核对token数量可能漏掉同长度模板变化；一致性通过也不证明任务表现相等。其工具代码由[原始论文](https://arxiv.org/abs/2611.16485)关联到[作者仓库](https://github.com/MinhThanghus/drydock-eval)，本库未执行。

候选筛选用于选下一位测试对象，确认时预先固定新任务、接受规则、失败计数和费用条件，并按仓库相关性计算不确定性。论文三个候选均未通过各自规则，第三个虽有正的点估计，仍未过其阈值；不能事后降低门槛。第三次重复使用128题留出集、后两次只注册四类条件，均需保留在解释中。未检出差异也不证明等效。隔离测试的200次通过针对作者部署树；公开替换标识的副本未重跑容器，容器共享内核的限制仍在。

## 界面结果取证与模型接管

五步循环中，“执行并观察”不等于“验证通过”。[VeriCUA](https://arxiv.org/abs/2610.40578)先整理任务和环境，再生成验收量规，用 GUI 或代码查询结果。动作历史说明做过什么，当前截图说明画面，文件、数据库或设置才可能证明持久结果；来源与时序由 Harness 标注，仲裁器检查证据引用。编者例：点击保存后，还应在有权限的范围读回目标文件，而不只采信按钮动画或执行者自报。

它是执行后的验证器，不是更强的动作执行器。在线模式允许未决弃权；离线模式在多路径未决时回退初始 VLM 判分，不能统一称“查不到就拒绝”。判定一致性还依赖参考标签和访问能力；记录判定覆盖、条件准确率、误报与查询成本。论文的快照、特权读取和只读工具限制不能直接移植为生产权限保证。[完整记录](papers.md#paper-2610.40578)。

如果问题是执行器可能失败，再读较早的 [LEASH](https://arxiv.org/abs/2610.22280)：从弱模型隐状态和成功/失败参考库估计风险，初始或运行中切到强模型；交接后弱模型在影子路径观察，可要求强模型重新考虑。它不训练语言模型权重，但仍拟合统计量并校准门控；99 参考任务与 262 测试任务分开，比较升级率用实际值而非名义预算。风险预测不等于强模型收益预测，额外监控也未隔离证明总有收益。[记录](papers.md#paper-2610.22280)。

这与人工监督是不同接口：切换模型、请求人工决定和授予执行权限分别记录。LEASH 的模型门控不是人工授权的实证；VeriCUA 的结果判定也不自动决定是否允许下一步写入。DynaRev 则提醒先更新当前目标，再评价持久结果，见[阅读路线](reading-path.md)。

## 上下文、权限和验收的三个接口

1. **上下文接口**：[MemGPT](https://arxiv.org/abs/2310.08560)用分层存储与分页解释“保存的信息如何进入模型”。信息进入哪种消息、作用于会话/项目/用户哪个范围，仍需由具体 Harness 说明。
2. **信任接口**：[CPE](https://arxiv.org/abs/2609.01222)研究低信任内容提升消息角色或跨范围持久化的路径。应分别记录内容来源、角色/范围与执行权限。它是运行攻击路径研究，与 Scanning the Harness 的配置审计不同；自动验证的传播与后续行为也分别计数，不能据此断言所有当前产品均存在同一漏洞。该论文仅用于本段解释，完整候选核验见周报。
3. **验收接口**：[Incident-Arena](https://arxiv.org/abs/2610.00648)把验证从补丁延伸到运行服务：恢复门、安全门、持续负载与重启检查。它有 20 个任务、每推理档 3 次试验，且使用不同模型/Harness 配置；主成功检查和另用 LLM judge 的奖励投机分析分开。读它学习验收设计，而不把得分归因给模型单独。

MCP 定义接口；业务授权与沙箱隔离仍需实现。官方[安全实践](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)讨论令牌透传、混淆代理和最小权限（2026-10-05 核对）。本段补充跨层机制；Codex 架构两页于 11 月 2 日核对，其他产品资料日期见页首。

## 保护是否有效：同时测正常任务与攻击效果

[HarnessSecurity-Bench](https://arxiv.org/abs/2610.07639)连接三种证据：配置审计发现暴露，CPE 分析信任传播路径，运行对照检查安全设置是否改变实际效果。它在固定 GLM-5.2、23 个任务、六种 Harness 中分别用确定性 oracle 检查任务效用和攻击效果，比较支持开关的机制，并计入 token 与执行时间。评估时先确认开关、其他权限和基准版本，再问保护是否留下正常完成路径、是否覆盖通向同一资源的其他执行路径。

**边界：**40 种 Harness 的静态机制矩阵有 112/400 项未知，未知不等于缺失。运行实验是容器和模拟服务，审批关闭条件使用固定 LLM 审查器；部分源码来自非官方镜像。论文结果不能直接代表当前 Codex/Claude Code 版本或真人审批效果。任务效用按通过的检查计数，攻击效果按攻击实例计数，分母不同，不能合并为一个成功率。作者提供的是[任务包与效用检查](https://github.com/TsingPig/HarnessSecurity-Benchmark)，本库未运行。

运行框架也可以成为优化对象。[VERSE](https://arxiv.org/abs/2610.02616)进一步区分执行器的 Harness 与改进器自己的 Harness；两层修改和不可改验证接口见 [RSI 专题](rsi.md)。

## 写入超时后先确认状态（2026-10-19）

五步循环里的“执行并观察”还要区分请求已发送、服务端已完成和客户端已收到回执。[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)区分协议错误与 `isError: true` 的工具执行错误；错误反馈能帮助改参数，但超时本身不能证明写操作未发生。以下是教学设计示例，非某个产品的现成保证。

以有权限的退款工具为例：

1. **调用前**：核对订单、金额、授权和当前状态；创建一次逻辑操作的标识，并保存参数和预期终态。
2. **响应超时**：将本地结果记为 `unknown`，按该操作标识查询服务端账本或回执。查到已完成就读回退款结果，再核验金额和唯一性。
3. **决定重试**：只有接口提供对应的幂等约定、且已查明可重试时，才复用原标识与原参数；同一标识换参数应拒绝。设置次数、退避和总预算。没有可查状态或幂等支持时，交由人工核对，保留未知结果。
4. **恢复后验收**：检查客户余额、订单状态和重复写入，再恢复后续计划；有副作用的补偿操作需要自己的业务条件与权限，不能假设“回退”能撤销外部世界。

这套例子依据 [AWS 的幂等 API 设计说明](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)：调用者标识表达同一意图，服务端还需让去重记录与业务写入满足原子性。一个本地去重集合不足以解决进程崩溃和并发。此处退款资料核对日期为 10 月 19 日，与页首两项 Codex 架构资料的日期分别记录。

[AgentPerturb](https://arxiv.org/abs/2610.21624)提供补充的评估阅读：输入缺失、冗余、错误分别施加到用户请求、规程、继承上下文与工具契约。它不是上述退款流程的有效性实验；其单轨迹、完成后选择的 Toolathlon 子集和未评分排除规则见[记录](papers.md#paper-2610.21624)。评估恢复时，分别记录原任务、扰动是否仍可解、恢复动作、额外调用和最终验证；工具/验证器故障造成的无评分结果保留为缺失。

## 从补丁验收到需求验收（2026-10-19）

[FDE-Gym](https://arxiv.org/abs/2610.22350)把交付物放回模拟客户环境，用未修改系统和专家参考锚定业务收益，并另扣事故影响与沟通成本。可接在 τ^τ-Bench 的 Agent 构建与 Incident-Arena 的恢复验收之后，问“做对了什么”和“是否改善目标”。分数允许为负，归一化均分不是成功百分比。脚本客户和隐藏约束不代表真人项目；本库没有运行该环境。

## 框架实现测试与任务评估分开

“补丁通过测试”首先检验任务结果，不能单独说明 Harness 的权限优先级、会话恢复、参数边界都实现正确。[Doc2Harness](https://arxiv.org/abs/2610.20344)先固定构建框架，让模型根据文档和接口骨架生成候选；冻结候选后，再用脚本 mock 模型驱动完整会话，从发往模型的请求、磁盘文件、退出码和命令输出检查行为。

关键是**正对照**：例如要检查拒绝写入，先确认会话确实到达该写入检查路径；若程序根本没运行，文件没改变也不能算权限实现通过。正对照是在验证观测前提，不给任务分母额外增加成功。论文以 19 模型各三次独立构建、328 用例报告结果；用例之间可能相关，模块数与分数的相关性也不是“减少模块必然更好”的因果证据。

其[作者仓库](https://github.com/YuyaoGe/doc2harness)只开放 94 场景（53 计分用例及 41 正对照），不能用公开子集直接复现全量排名。固定构建器、接口和预算限制了解释范围；它没有测冻结后的行为反馈修复，更没有证明 RSI。学习时分三层留证：实现契约是否符合 → 真实模型是否完成目标任务 → 后续版本是否在留出任务改善。它们互补，不能拿一层分数代替另两层。

## 从接口契约到过程可执行性

Doc2Harness 检查实现契约；[Prefix Executability](https://arxiv.org/abs/2610.40444)补检查已执行轨迹：参数是否合规、依赖值是否已有、动作前提是否成立、状态是否一致。基准侧确定性检查器在首个无效动作停止前缀评分，但原始完整轨迹仍用于最终成功及恢复率。编者例：先用不存在的联系人 ID 删除失败，再查得正确 ID 并成功，结果成功不能把首个无效步骤改成有效。反之，全程可执行也可能完成了错误目标。

读指标时保留三个分母：PEC 用固定样本集合并要求到达该深度，下降也可能来自提前结束；TER 看完整轨迹是否一直可执行；RR 只在出现无效前缀的轨迹中计最后恢复成功。计划/验证器的推理不进入动作长度，却必须计入 token 和时延。事前 LLM 验证器也不是事后的确定性检查器；基准可见状态之外的语义、授权与安全仍需另评。

作者在 BFCL-v3 和 ToolSandbox 各 200 任务、三模型四方法上比较，并加测 tau³-bench 的 Airline50/Retail114。后两域的独立敏感性试验中，TER/AUC-PEC 配对差异区间都含零，且验证有额外成本，不能写成“多一个检查器必然更可靠”。这些区间刻画任务变化，不是同一任务重复运行的不确定性。[实验范围](papers.md#paper-2610.40444)。

## 环境是回放、模拟还是在线服务？

[ToolSpace](https://arxiv.org/abs/2611.05036)按数据流、对象状态变化和失败后成功切换工具的记录建图；修改型环境按需合成数据库，查询型环境恢复快照，无状态调用可重用缓存返回。随后按状态游走，失败时回滚重采样，再生成终态、关键轨迹与输出断言，从初态重放筛选。这个顺序是先有可执行链、再写任务，而不是只从任务文字猜工具接口。

回放中的状态连续、模拟环境的任务可解、线上服务的语义与副作用一致，是不同检查。缓存不暴露真实服务后续变更；构造链与断言的共同遗漏也可能通过重放。原论文v1的两套Pro任务为300/98，作者本地结果三次均值，外部成绩按其发布值；不能按混合原生指标的平均数判断部署可靠性。[作者代码](https://github.com/dongguanting/ToolSpace)入口已核对，未运行；仓库一处600题描述与原PDF/HTML不同，采用原文分母，详见[核验日志](https://github.com/Scodive/AI-Agent-Guide/blob/main/data/verification-notes.md)。

可将它接在Doc2Harness与Prefix之后：框架是否实现约定 → 轨迹动作是否合法 → 任务与断言怎样构造 → 最终目标是否满足。开发/测试用的可回滚环境不能自动赋予真实业务动作可逆性。

## 证据缺失：先查证，再决定执行

前面的退款例子处理“动作效果未知”；[EpiSEM-Bench](https://arxiv.org/abs/2610.31650)处理“执行前提未知”。例如同一笔 42,800 元付款，审批上限为 30,000 时禁止、50,000 时允许；若工具省略上限，其余返回值仍可全都真实。查证恢复上限后，Agent 应分别停止和执行。这个例子来自论文的模拟付款任务，不是实际付款测试。

基准在完整私有状态上判定动作，普通观察持续抑制所选事实；恢复接口须由 Agent 主动调用。六领域 300 对任务/600 世界、十模型，每条件一条轨迹、12 步预算。读结果时同时区分：有没有获取证据、是否在获取前就执行、证据恢复后能否正确行动、允许世界是否误拒绝，以及查证开销。查证次数不是有用恢复，低违规率也可能来自一律拒绝。

其 UCR 按“出现过任一违规”的任务数除以 300，不能解释成每次调用的事故概率；自适应搜索产生的遗漏集合依模型不同，恢复对照须对齐相同世界和遗漏集合。此机制补 [AgentPerturb](papers.md#paper-2610.21624) 的交互扰动，并与 [HarnessSecurity-Bench](papers.md#paper-2610.07639) 的攻击/效用对照并列：错误信息、真实但不完整的信息、恶意指令及权限执行分别检验。MCP 工具返回 `isError=false` 或符合结构，也不保证业务证据完整；其[工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)核对于 2026-10-26。


## 意图声明、授权与环境证据

[Intent Contracts](papers.md#paper-2611.24025)将规划器的直接工具权限移走：规划器提交目标、用户原句和作用域；代码先校验，受信执行模型再生成一次调用，可只完成获准部分。这连接了五步循环里的“提出行动”和“真正分发”，让每个效果可追溯到调用前的声明。

但声明完整、授权正确、能力受限是三项检查。原文的执行器看不到环境和工具结果，无法判断歧义指代究竟指哪个文件；契约并未比盲审减少未授权动作。其部分范围检查还不能约束任意shell写入，实验未开启出站命令检查，不能把它当通用沙箱。应同时保留目标取证、执行环境权限和结果回读；这些是阅读此机制的检查点，不是该论文已验证的完整修复。

读实验时先看三类96提示来自16模板、每条件单次，再看附加文件任务的重复；重复同一模板不能当新任务。与现有CPE/HarnessSecurity-Bench互补：来源可信度、正常效用、攻击结果和意图可追溯分别测。代码由[原文](https://arxiv.org/html/2611.24025v1)关联到[作者仓库](https://github.com/zwang-devv/intent-contracts)，本库未运行。

## 普通故障下的恢复权限

较早工作[Agent Meltdowns](papers.md#paper-2605.19149)于5月首交、11月18日修订，本周补读v2。七类受控文件/依赖/权限/网络故障显示，目标导向的恢复也可能越界，并不要求恶意提示。对Coding Agent，应分开记录错误、恢复提案、是否获准、实际副作用和最终汇报；遇到权限拒绝不自动获得修改权限的权力。写入超时查状态的路线继续保留。

论文1297/2000的汇总包含计划和尝试阶段的中高风险标签，不是已成功执行有害操作的比例，更不是真实部署事故率。部分场景给予广权限与passwordless sudo，模型/预算/样本并不完全匹配，LLM分类仍有人工抽样不确定性。先核对生命周期与分母，再比较恢复策略，不能仅用长轨迹相关性解释机制。原文关联[作者任务包](https://github.com/htried/meltdowns)，未执行。
