# Agent Harness：Coding Agent 如何工作

*论文与证据恢复资料增补核对：2026-10-26；Codex 产品资料沿用 2026-09-27。旧论文日期见论文库；产品行为以链接的官方文档为准。*

**Harness（运行框架）**是围绕模型组织任务、工具、执行环境和反馈的程序。模型决定下一步要做什么；harness 决定它能看到哪些信息、怎样调用工具、命令在哪里执行、结果如何回到上下文，以及何时验证、停止或请人介入。不要把模型、harness、执行环境和评测任务混成一个“Agent 能力”数字。[OpenAI 官方架构说明](https://developers.openai.com/api/docs/guides/agents-api/architecture)明确区分 harness、environment 和 application server；[Code as Agent Harness](https://arxiv.org/abs/2605.18747)从研究角度梳理这些层次。

## 一个 Coding Agent 的工作循环

1. **接收任务和仓库上下文**：目标、约束、文件、已有差异、项目说明和可用工具进入会话。
2. **选择动作**：模型根据当前上下文提出检索、读取文件、编辑代码或运行命令等动作。
3. **执行并观察**：harness 把动作交给有权限的工具或沙箱；输出、错误和文件变化返回会话。
4. **验证与修复**：运行相关测试、构建或人工可检查的演示；失败时根据反馈修改，而非只凭“代码已写”结束。
5. **交付与监督**：展示差异、验证结果及剩余风险；需要权限或方向判断时交由人决定。

**先看固定流程基线。**[Agentless](https://arxiv.org/abs/2407.01489)把仓库修复组织为定位、补丁生成、验证三个预定阶段，模型不自主决定下一种工具动作；程序仍执行检索、测试和候选筛选。对照 SWE-agent 的动态动作循环与 SWE-Search 的分支搜索，问新增自由度解决了什么失败、花了多少预算。Agentless v2 的 SWE-bench Lite 结果是历史快照，且每题最多生成 40 个补丁和 40 个复现测试；固定流程也有采样成本，不能直接用异模型榜单证明其总是更优。[完整记录](papers.md#paper-2407.01489)。

这是一种**概念性拆解**，不是某个产品内部代码的逐行复刻。[OpenAI 对 Codex 长任务的说明](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)将其概括为计划、编辑、运行工具、观察、修复和重复；[官方 Agents API 文档](https://developers.openai.com/api/docs/guides/agents-api/overview)说明 Codex harness 管理会话、编排、上下文压缩与恢复，执行环境负责命令和文件。Codex 是帮助理解这一结构的实例，不等于所有 Coding Agent 共用同一实现。

## 近期延伸阅读（2026-10-03）

- [Beyond the Model](https://arxiv.org/abs/2609.32459)：先看固定模型的框架比较，再看组件消融。读图时分清基准总规模与实际抽样数；压缩和通用子 Agent 在所测仓库生成任务中可能降分。
- [Mingbird](https://arxiv.org/abs/2610.02001)：看工具预填充、循环检测与完成检查如何适配小模型。主实验只在一台 Windows 机器上进行；单组件结果的波动限制了归因。
- [VISTA](https://arxiv.org/abs/2610.02200)：将 Harness 视角延伸到视觉交互。核心是保留原始帧并主动回看、放大和读取像素；公开游戏成绩仍需留出环境检验。

这些是拓展阅读，均按预印本记录；完整实验范围见[论文库](papers.md)。

## 阅读 Codex 时应分清的边界

- **Codex 模型与 Codex harness**：模型产生判断与工具请求；harness 维护循环和会话，连接工具与执行环境。不同运行方式提供的工具、权限和环境可能不同。以上以[OpenAI 官方架构文档](https://developers.openai.com/api/docs/guides/agents-api/architecture)为准。
- **仓库指令与验证**：`AGENTS.md`、技能或任务说明可以给出项目约束；它们不能代替运行测试、检查差异和确认交付条件。[OpenAI 的长任务案例](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)是一个有说明文件和阶段验证的实例，不是所有任务的效果保证。
- **安全边界**：工具可访问的文件、网络与凭据取决于执行环境；评估 Coding Agent 时应记录权限、沙箱和人工审批设置。[官方环境文档](https://developers.openai.com/api/docs/guides/agents-api/architecture)区分托管与自有执行环境。

**推荐顺序：**先用 Agentless 理解固定流程，再用 SWE-agent 理解动态动作与接口，读 Codex 官方架构理解产品中的循环，之后用 The Scaffold Effect 和 DAREBench 检查模型、框架和工作负载的比较边界。相关论文的研究问题、指标、局限与核验日期见[论文库](papers.md)。

## 上下文、权限和验收的三个接口

1. **上下文接口**：[MemGPT](https://arxiv.org/abs/2310.08560)用分层存储与分页解释“保存的信息如何进入模型”。信息进入哪种消息、作用于会话/项目/用户哪个范围，仍需由具体 Harness 说明。
2. **信任接口**：[CPE](https://arxiv.org/abs/2609.01222)研究低信任内容提升消息角色或跨范围持久化的路径。应分别记录内容来源、角色/范围与执行权限。它是运行攻击路径研究，与 Scanning the Harness 的配置审计不同；自动验证的传播与后续行为也分别计数，不能据此断言所有当前产品均存在同一漏洞。该论文仅用于本段解释，完整候选核验见周报。
3. **验收接口**：[Incident-Arena](https://arxiv.org/abs/2610.00648)把验证从补丁延伸到运行服务：恢复门、安全门、持续负载与重启检查。它有 20 个任务、每推理档 3 次试验，且使用不同模型/Harness 配置；主成功检查和另用 LLM judge 的奖励投机分析分开。读它学习验收设计，而不把得分归因给模型单独。

MCP 定义接口；业务授权与沙箱隔离仍需实现。官方[安全实践](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)讨论令牌透传、混淆代理和最小权限（2026-10-05 核对）。本段补充跨层机制；前文 Codex 产品资料的核对日期仍为 2026-09-27。

## 保护是否有效：同时测正常任务与攻击效果

[HarnessSecurity-Bench](https://arxiv.org/abs/2610.07639)连接三种证据：配置审计发现暴露，CPE 分析信任传播路径，运行对照检查安全设置是否改变实际效果。它在固定 GLM-5.2、23 个任务、六种 Harness 中分别用确定性 oracle 检查任务效用和攻击效果，比较支持开关的机制，并计入 token 与执行时间。评估时先确认开关、其他权限和基准版本，再问保护是否留下正常完成路径、是否覆盖通向同一资源的其他执行路径。

**边界：**40 种 Harness 的静态机制矩阵有 112/400 项未知，未知不等于缺失。运行实验是容器和模拟服务，审批关闭条件使用固定 LLM 审查器；部分源码来自非官方镜像。论文结果不能直接代表当前 Codex/Claude Code 版本或真人审批效果。任务效用按通过的检查计数，攻击效果按攻击实例计数，分母不同，不能合并为一个成功率。作者提供的是[任务包与效用检查](https://github.com/TsingPig/HarnessSecurity-Benchmark)，本库未运行。

运行框架也可以成为优化对象。[VERSE](https://arxiv.org/abs/2610.02616)进一步区分执行器的 Harness 与改进器自己的 Harness；两层修改和不可改验证接口见 [RSI 专题](rsi.md)。

## 写入超时后先确认状态（2026-10-19）

五步循环里的“执行并观察”还要区分请求已发送、服务端已完成和客户端已收到回执。[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)区分协议错误与 `isError: true` 的工具执行错误；错误反馈能帮助改参数，但超时本身不能证明写操作未发生。以下是教学设计示例，非某个产品的现成保证。

以有权限的退款工具为例：

1. **调用前**：核对订单、金额、授权和当前状态；创建一次逻辑操作的标识，并保存参数和预期终态。
2. **响应超时**：将本地结果记为 `unknown`，按该操作标识查询服务端账本或回执。查到已完成就读回退款结果，再核验金额和唯一性。
3. **决定重试**：只有接口提供对应的幂等约定、且已查明可重试时，才复用原标识与原参数；同一标识换参数应拒绝。设置次数、退避和总预算。没有可查状态或幂等支持时，交由人工核对，保留未知结果。
4. **恢复后验收**：检查客户余额、订单状态和重复写入，再恢复后续计划；有副作用的补偿操作需要自己的业务条件与权限，不能假设“回退”能撤销外部世界。

这套例子依据 [AWS 的幂等 API 设计说明](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)：调用者标识表达同一意图，服务端还需让去重记录与业务写入满足原子性。一个本地去重集合不足以解决进程崩溃和并发。资料核对日期为 10 月 19 日，不刷新前文 Codex 产品日期。

[AgentPerturb](https://arxiv.org/abs/2610.21624)提供补充的评估阅读：输入缺失、冗余、错误分别施加到用户请求、规程、继承上下文与工具契约。它不是上述退款流程的有效性实验；其单轨迹、完成后选择的 Toolathlon 子集和未评分排除规则见[记录](papers.md#paper-2610.21624)。评估恢复时，分别记录原任务、扰动是否仍可解、恢复动作、额外调用和最终验证；工具/验证器故障造成的无评分结果保留为缺失。

## 从补丁验收到需求验收（2026-10-19）

[FDE-Gym](https://arxiv.org/abs/2610.22350)把交付物放回模拟客户环境，用未修改系统和专家参考锚定业务收益，并另扣事故影响与沟通成本。可接在 τ^τ-Bench 的 Agent 构建与 Incident-Arena 的恢复验收之后，问“做对了什么”和“是否改善目标”。分数允许为负，归一化均分不是成功百分比。脚本客户和隐藏约束不代表真人项目；本库没有运行该环境。

## 框架实现测试与任务评估分开

“补丁通过测试”首先检验任务结果，不能单独说明 Harness 的权限优先级、会话恢复、参数边界都实现正确。[Doc2Harness](https://arxiv.org/abs/2610.20344)先固定构建框架，让模型根据文档和接口骨架生成候选；冻结候选后，再用脚本 mock 模型驱动完整会话，从发往模型的请求、磁盘文件、退出码和命令输出检查行为。

关键是**正对照**：例如要检查拒绝写入，先确认会话确实到达该写入检查路径；若程序根本没运行，文件没改变也不能算权限实现通过。正对照是在验证观测前提，不给任务分母额外增加成功。论文以 19 模型各三次独立构建、328 用例报告结果；用例之间可能相关，模块数与分数的相关性也不是“减少模块必然更好”的因果证据。

其[作者仓库](https://github.com/YuyaoGe/doc2harness)只开放 94 场景（53 计分用例及 41 正对照），不能用公开子集直接复现全量排名。固定构建器、接口和预算限制了解释范围；它没有测冻结后的行为反馈修复，更没有证明 RSI。学习时分三层留证：实现契约是否符合 → 真实模型是否完成目标任务 → 后续版本是否在留出任务改善。它们互补，不能拿一层分数代替另两层。

## 证据缺失：先查证，再决定执行

前面的退款例子处理“动作效果未知”；[EpiSEM-Bench](https://arxiv.org/abs/2610.31650)处理“执行前提未知”。例如同一笔 42,800 元付款，审批上限为 30,000 时禁止、50,000 时允许；若工具省略上限，其余返回值仍可全都真实。查证恢复上限后，Agent 应分别停止和执行。这个例子来自论文的模拟付款任务，不是实际付款测试。

基准在完整私有状态上判定动作，普通观察持续抑制所选事实；恢复接口须由 Agent 主动调用。六领域 300 对任务/600 世界、十模型，每条件一条轨迹、12 步预算。读结果时同时区分：有没有获取证据、是否在获取前就执行、证据恢复后能否正确行动、允许世界是否误拒绝，以及查证开销。查证次数不是有用恢复，低违规率也可能来自一律拒绝。

其 UCR 按“出现过任一违规”的任务数除以 300，不能解释成每次调用的事故概率；自适应搜索产生的遗漏集合依模型不同，恢复对照须对齐相同世界和遗漏集合。此机制补 [AgentPerturb](papers.md#paper-2610.21624) 的交互扰动，并与 [HarnessSecurity-Bench](papers.md#paper-2610.07639) 的攻击/效用对照并列：错误信息、真实但不完整的信息、恶意指令及权限执行分别检验。MCP 工具返回 `isError=false` 或符合结构，也不保证业务证据完整；其[工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)核对于 2026-10-26。
