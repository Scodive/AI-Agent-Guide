# 收录标准与每周更新 SOP

论文库是**人工精选的研究入口**。每周同时审查近期论文、整个指南的讲述逻辑和现有技术路线的覆盖情况；每次交付详细分析及可审阅的本地修改，由维护者决定是否提交。没有合格论文时允许零新增，仍须检查已有内容的准确性、结构与缺失。不要把 arXiv 检索结果直接作为已收录论文。

## 收录边界

1. 与 LLM Agent 的架构、Harness 与运行时、规划、工具、记忆、交互环境、多智能体、评估、安全或自我演进直接相关。纯模型推理或对齐论文只有在帮助理解 Agent 机制时才作为“基础方法”收录。RSI 条目要写清被改进的是提示词、Agent 程序、目标算法还是模型参数。
2. 优先保留定义了重要问题、提出可辨认机制、给出可检查实验，或为某方向提供可靠综述的论文。引用数、GitHub stars 和“顶会”标签都不是单独的准入条件；新预印本也可收录，但须标明来源状态。
3. 有稳定论文页面，标题、作者、年份、编号能与该页面匹配。代码链接须指向作者或项目明确关联的仓库；没有确认就留空。
4. 与现有条目重复或仅是同一研究的新版本时，更新原记录，不新增一行。无法核对、与 Agent 仅弱相关或只有宣传页的候选暂缓。
5. 记录问题、机制、环境与指标、主要结论、局限时，以论文原文为依据；无法核验的数值或发表状态不写。结论只写论文支持的范围，不把单一基准表现写成部署可靠性。

## 每周操作

| 步骤 | 人工动作 | 留下的记录 |
| --- | --- | --- |
| 1. 确认基线 | 读取仓库状态、上期报告、待审修改和所有导读；记录本次基准提交。保留维护者及上期尚未批准的修改。 | 周报中的基线、审查范围与遗留事项。 |
| 2. 收集与初筛 | 查看最近一周的 arXiv、OpenReview、ACL Anthology、CVF/PMLR 等原始页面，并追查有助于补齐技术路线的早期漏项及旧论文新版本。去重并判断学习价值。 | 在 `data/candidate-log.md` 记录标题、来源、提交/修订日期及去留理由。 |
| 3. 核验 | 核对标题、作者、编号和来源状态；阅读方法、实验与局限，确认代码归属。产品机制使用对应官方文档并与论文分开。 | 更新核验记录，明确作者报告、未复现、探索性或未知证据。 |
| 4. 整库技术与讲述审查 | 对每条技术路线检查研究问题、机制、证据、边界及前置知识；分析新方法如何补充、替代或挑战已有讲解。按下方审查维度记录覆盖情况。 | 详细周报，包含结构问题、技术缺失、修订理由与优先级。 |
| 5. 编辑 | 维护 CSV、中英文指南、阅读路线、Harness、RSI、精选及导航。通常精选 3–5 篇，依据价值决定数量；修改应对应明确的问题和证据。 | 本地差异及逐文件修改清单，区分本周新增与既有待审修改。 |
| 6. 检查与交付 | 运行 `python3 scripts/render_catalog.py` 和 `python3 scripts/render_catalog.py --check`，检查字段、链接、分类和阅读顺序，确认独立网站读取的来源路径仍存在。 | 保存 `data/weekly-reviews/YYYY-MM-DD.md`，向维护者汇报发现、具体改动、待核验项与检查结果。 |
| 7. 维护者审核 | 等维护者查看周报与差异，并明确决定是否提交。获准后再提交、推送，随后检查独立网站同步结果。 | 记录审核决定、实际提交及网站核验状态。 |

每月最后一周，更新[本月精选](monthly-picks.md)，回看分类是否需要调整，并抽查旧条目的链接与发表状态。历史精选可移入 `docs/archive/`。

## 每周必须覆盖的分析维度

1. **整库技术覆盖**：逐一检查综述与架构、规划与推理、工具与行动、记忆与检索、感知与 GUI、代码智能体、Harness 与运行时、自我演进/RSI、多智能体、系统与应用、评估与安全。对各方向明确写“覆盖充分 / 讲解薄弱 / 存在缺失 / 内容过时 / 本周未完成核验”，并以章节和来源解释判断。不能只列论文数量。
2. **讲述逻辑**：入口是否先解释研究问题；术语是否一致；前置知识和阅读顺序是否合理；章节是否重复或跳步；问题、机制、实验和局限是否对应；中英文指南、主题导读和阅读路线是否一致。保留有学习价值的经典路线，说明新旧关系。
3. **新技术对讲解的影响**：每项建议指出原文位置、现有讲解的具体不足、新方法增加的认知价值、支持来源和建议改法。区分“替代旧方法”“补充机制”“提供反例或边界”“暂待观察”，不以论文发布日期决定是否重写。
4. **技术路线缺失**：补查尚未收录的代表作、重要基线、关键接口和运行机制、评估协议与实际部署约束；区分缺少论文、缺少机制解释、缺少路线连接和缺少实验依据。较早工作也可以是本周的重要补充。
5. **证据与适用范围**：分清模型、运行框架、执行环境和工作负载；RSI 写清修改对象与反馈来源。核对预算、基准版本、分母、数据泄漏、统计不确定性、成本与失败类型，不把预印本或产品案例写成已验证的通用结论。
6. **改动与剩余事项**：给出每个修改文件的“原问题 → 改动 → 理由 → 来源 → 检查结果”；列明未完成的核验和保留原文的原因。详细周报按[固定模板](weekly-review-template.md)填写，聊天汇报提供可点击的报告与文件链接。

## 每周交付与提交边界

- 每次保存一份真实填写的周报，记录检索窗口、基准版本和实际阅读范围；无法完成某项审查时明确说明，不能写成整库已经核验。
- 修改先保留在本地供维护者审阅；每次周更须等待本次明确批准后再执行 `git add`、commit、push 或创建 PR。此前某次发布许可不自动延续到下一周。
- 不恢复旧站点构建或部署配置，不修改独立展示网站的业务、权限或发布设置。网站同步是否成功须单独核验。
- 下一周存在尚未审核的修改时，保留它们并在新周报中区分本周增量，不覆盖、撤销或代替维护者作出提交决定。

## CSV 字段

`data/papers.csv` 是唯一论文数据源。`docs/papers.md` 是**手动运行脚本后生成**的仓库 Markdown 表格；不要直接编辑生成表格。中英文完整指南分别维护在根目录 `README.md` 和 `README_EN.md`。独立展示网站读取 CSV 与专题 Markdown，使用自身的构建和发布流程。

| 字段 | 填写规则 |
| --- | --- |
| `id`, `title`, `year`, `paper_url` | arXiv 编号、原始标题、首次上载年份及摘要页；四者须匹配。 |
| `topic`, `type`, `route` | 主主题、论文类型、入门或拓展。类型区分综述、方法、基准、系统/工具等。 |
| `question`, `mechanism` | 一句话写研究问题与关键机制。 |
| `evaluation` | 写实际环境及指标类别；综述写“无统一实验指标”。 |
| `conclusion`, `limitation` | 分别写论文支持的结论及适用边界；避免未经核对的数字。 |
| `code_url` | 已确认的官方代码；没有则留空。 |
| `verified_on`, `source_status` | 最近核验日期；来源或发表状态。未经确认的会议录信息不可写成已录用。 |

`render_catalog.py` 仅使用 Python 标准库，在维护者主动运行时校验 CSV 并生成仓库表格，**没有定时抓取或自动收录论文**。本仓库不构建或部署网站；展示网站的同步和发布由该网站项目管理。
