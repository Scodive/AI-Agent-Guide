# 收录标准与每周更新 SOP

论文库是**人工精选的研究入口**。每周花约 60–90 分钟处理候选即可；新的一周没有合格论文时，允许零新增。不要把 arXiv 检索结果直接作为已收录论文。

## 收录边界

1. 与 LLM Agent 的架构、Harness 与运行时、规划、工具、记忆、交互环境、多智能体、评估、安全或自我演进直接相关。纯模型推理或对齐论文只有在帮助理解 Agent 机制时才作为“基础方法”收录。RSI 条目要写清被改进的是提示词、Agent 程序、目标算法还是模型参数。
2. 优先保留定义了重要问题、提出可辨认机制、给出可检查实验，或为某方向提供可靠综述的论文。引用数、GitHub stars 和“顶会”标签都不是单独的准入条件；新预印本也可收录，但须标明来源状态。
3. 有稳定论文页面，标题、作者、年份、编号能与该页面匹配。代码链接须指向作者或项目明确关联的仓库；没有确认就留空。
4. 与现有条目重复或仅是同一研究的新版本时，更新原记录，不新增一行。无法核对、与 Agent 仅弱相关或只有宣传页的候选暂缓。
5. 记录问题、机制、环境与指标、主要结论、局限时，以论文原文为依据；无法核验的数值或发表状态不写。结论只写论文支持的范围，不把单一基准表现写成部署可靠性。

## 每周操作

| 步骤 | 人工动作 | 留下的记录 |
| --- | --- | --- |
| 1. 收集（10–15 分钟） | 查看 arXiv、OpenReview、ACL Anthology、CVF/PMLR 等原始页面，以及社区推荐和 Issue。 | 在 `data/candidate-log.md` 记标题、链接、发现日期。 |
| 2. 初筛（15 分钟） | 去重，判断与现有主题和阅读路线的关系；优先补重要空缺。 | 给候选标注“待核验 / 暂缓 / 拒收”。 |
| 3. 核验（20–30 分钟） | 打开论文原始页面，核对标题、作者、编号、发表状态；阅读摘要、方法和实验；确认代码归属。 | 将来源和收录理由写入候选日志。 |
| 4. 编辑（15–20 分钟） | 在 `data/papers.csv` 新增或修订记录；写清实验环境与局限。每周建议最多 3–5 篇。 | 更新 `verified_on`；必要时调整阅读路线或本月精选。 |
| 5. 发布前检查（10 分钟） | 手动运行 `python3 scripts/render_catalog.py` 和 `python3 scripts/render_catalog.py --check`；查看表格筛选和链接。 | PR 中写本周新增、修订、暂缓数及主要更正。 |

每月最后一周，更新[本月精选](monthly-picks.md)，回看分类是否需要调整，并抽查旧条目的链接与发表状态。历史精选可移入 `docs/archive/`。

## CSV 字段

`data/papers.csv` 是唯一论文数据源。`docs/papers.md` 以及站内中英文完整指南是**手动运行脚本后生成**的文件；不要直接编辑生成页。

| 字段 | 填写规则 |
| --- | --- |
| `id`, `title`, `year`, `paper_url` | arXiv 编号、原始标题、首次上载年份及摘要页；四者须匹配。 |
| `topic`, `type`, `route` | 主主题、论文类型、入门或拓展。类型区分综述、方法、基准、系统/工具等。 |
| `question`, `mechanism` | 一句话写研究问题与关键机制。 |
| `evaluation` | 写实际环境及指标类别；综述写“无统一实验指标”。 |
| `conclusion`, `limitation` | 分别写论文支持的结论及适用边界；避免未经核对的数字。 |
| `code_url` | 已确认的官方代码；没有则留空。 |
| `verified_on`, `source_status` | 最近核验日期；来源或发表状态。未经确认的会议录信息不可写成已录用。 |

`render_catalog.py` 只在维护者主动运行时生成静态页面，**没有定时抓取、自动收录或自动发布论文**。现有 GitHub Pages 流程仍负责网站部署。
